# Card/environment lifecycle authority

The SQLite workflow aggregate is authoritative at mutation boundaries. `kanban_cards` stores project/provider binding, parent edge, stored leaf workflow state and workflow revision; `hierarchy_finalized` is a persisted provider-finalization fact, **not** proof that there are no children. Linked children (including a parent with a stale zero flag) make an aggregate. A verified zero-child, non-finalized card can be a leaf. The displayed aggregate status is derived from descendants, not a second workflow. Aggregate leaf actions must be rejected by the backend even when a client cached a capability.

`card_environments` stores a single owned environment per card (id, project, repository, checkout, branch, revision and lifecycle); `card_panes` and `card_layouts` belong to that exact environment. Creation operations record setup ownership and Git inventory, not an environment. A card cannot attach twice, attach while cleanup owns it, or attach setup evidence from another project/repository/target/branch/revision. Preflight Git checks run outside SQLite write locks; the final insert checks workflow and binding evidence in the same SQLite savepoint. A rejected setup may need its guarded compensation; it does not silently overwrite an existing environment.

`card_cleanup_operations` records immutable environment id/revision, workflow revision, exact source/target and phase. A live captured environment must match both id and revision. Missing metadata is resumable only after registration validation at `remove_metadata`/`record_completion`, or after a completed operation; a changed/replacement environment is never evidence of completion. Completion requires metadata absence and leaves an audit event. Phase and failure commits are durable; a failed cleanup does not imply permission to delete unrelated resources. Pi/PTy runtime registries own live sessions; pane ids in the cleanup snapshot identify sessions to stop, while Git validation/registered worktrees and exact branch tips own repository side effects. Filesystem absence alone does not validate cleanup. Other delivery operations retain their own revision-bearing snapshots.

`environment_health` is read-only (one DB connection for a batch of requested cards), reports parent/environment and cleanup/environment mismatches without emitting events or modifying revisions. It does not reconcile Superthread relationships: parent-specific recovery belongs to #197's guarded provider preflight. No generic make-parent override exists.

Response meanings: completed cleanup with the captured environment gone is idempotent; missing environment before verified removal, replacement id/revision, and stale workflow evidence are conflicts requiring reload/inspection; failed or partial cleanup keeps its durable phase and must be resumed only against the original evidence. No-op reads or audits must not bump board revisions. The current command API returns actionable `conflict:` errors for these cases; a structured Rust–TypeScript error contract is deferred to the separate contract card.
